# Release 0.10.0 recovery

This PR fixes the release workflow failures after [#262](https://github.com/rocketclimb/rocketicons/pull/262) merged. The website deployment succeeded.

## npm: the immediate problem

The early attempts failed with npm E404. The maintainer reported publishing the packages manually, then retrying. That is consistent with an npm permission or first-publication setup issue; repository metadata was not established as the cause.

The old workflow skipped existing `utils` and `tailwind` versions, but deliberately failed for existing `toolkit`, `mcp` and `rocketicons` versions. That prevented the same manual recovery from working for every package. [Attempt 5](https://github.com/rocketclimb/rocketicons/actions/runs/36251805921/attempts/5) also tried to publish toolkit after its lookup missed the version; npm rejected the write because `0.2.0` already existed. The logs do not prove whether the lookup missed it because of registry delay or a concurrent publication.

**Implemented fix:** skip an already-published version for every package when its archive matches the prepared release. Different archive contents still stop the release. Prefer fresh registry reads, and check again after a failed publish before deciding that the release failed. This covers manual publication and short registry delays without publishing a second build under the same version.

Anonymous npm checks confirmed these three public packages exactly match the prepared archives:

| Package                 | Version | State at verification        |
| ----------------------- | ------- | ---------------------------- |
| `@rocketicons/utils`    | `0.8.0` | Published, identical archive |
| `@rocketicons/tailwind` | `0.8.0` | Published, identical archive |
| `@rocketicons/toolkit`  | `0.2.0` | Published, identical archive |
| `@rocketicons/mcp`      | `0.2.0` | Not yet published            |
| `rocketicons`           | `0.4.0` | Not yet published            |

**Removed after review:** the proposed token fallback, disabling OIDC/provenance for old archives, and package repository-metadata edits. Those were not needed to fix the skip behavior. The existing npm authentication mechanism stays in place. An npm package administrator still needs to authorize publication of new packages; changing release code cannot grant that permission. See [npm's trusted-publisher configuration](https://docs.npmjs.com/trusted-publishers/) for the package-side settings.

## Two separate failures also addressed

- **Cut lookup:** the [first publication attempt](https://github.com/rocketclimb/rocketicons/actions/runs/36251805921/attempts/1) missed the successful Cut Release run; the lookup worked later. The workflow now reads the exact run URL recorded in the PR, checks its identity, and retries failed API reads. The cause of the first miss remains unconfirmed.
- **Branch sync:** the [sync job](https://github.com/rocketclimb/rocketicons/actions/runs/36251805926) hit add/add conflicts after the squash merge. The prepared release head and squash commit have identical Git trees. After verifying that equality and the cut source's ancestry in `develop`, the fix reconnects their history and performs a normal merge. Later changes are preserved; genuine conflicts abort, and pushes never force-replace the branch. The search for a release is bounded to the latest 30 main commits since the common ancestor.

## Recover after merging

1. Confirm npm publishing access for the remaining packages. A maintainer can bootstrap a package manually using the exact prepared archive; the updated workflow will recognize and skip it.
2. Run **Release Packages** on **main**, with `release_pr` set to `262`. This uses the updated workflow with the original cut run `36250310169` and unchanged versions/artifacts. Rerunning an old job loads the old workflow.
3. The workflow reuses `v0.10.0-release` only if it points to the original merge commit `86943b1493ac82016e18ef535c8e03d4451a0cdb`. It publishes or verifies all five packages in dependency order, then creates the GitHub release.
4. Merging this fix also runs **Sync main into develop** automatically. The sync workflow can be run manually on main if needed.
5. Verify the final public versions and a fresh installation. Local tests do not prove npm publishing permissions.

`npm run test:release` covers lookup identity, bounded retries, tag identity, partial publication, manual-publication races, delayed registry reads, archive mismatches, package ordering, and real Git merge fixtures. Recovery stops on missing artifacts, different existing bytes, a mismatched tag or genuine merge conflicts.
